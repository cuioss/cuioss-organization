= Organization Secrets
:toc:

== Overview

This document defines which secrets should be managed at organization level vs repository level.

== Organization-Level Secrets

These secrets are **shared across all repositories** and should be configured once at the organization level.

Set at: `https://github.com/organizations/cui-oss/settings/secrets/actions`

[cols="1,2,1"]
|===
|Secret |Purpose |Used By

|`RELEASE_APP_ID`
|cuioss-release-bot GitHub App ID
|maven-release.yml

|`RELEASE_APP_PRIVATE_KEY`
|cuioss-release-bot private key (.pem)
|maven-release.yml

|`OSS_SONATYPE_USERNAME`
|Maven Central / Sonatype OSSRH username
|maven-build.yml, maven-release.yml

|`OSS_SONATYPE_PASSWORD`
|Maven Central / Sonatype OSSRH password
|maven-build.yml, maven-release.yml

|`GPG_PRIVATE_KEY`
|GPG private key for artifact signing
|maven-build.yml, maven-release.yml

|`GPG_PASSPHRASE`
|GPG key passphrase
|maven-build.yml, maven-release.yml

|`SONAR_TOKEN`
|SonarCloud authentication token
|maven-build.yml

|`RELEASE_APP_ID_<OWNER>`
|App ID of another organisation's own release App (see below). Currently: `RELEASE_APP_ID_PLAN_MARSHALL`
|release.yml (cuioss-organization), maven-release.yml of a library with consumers there

|`RELEASE_APP_PRIVATE_KEY_<OWNER>`
|Private key (.pem) of that App. Currently: `RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL`
|release.yml (cuioss-organization), maven-release.yml of a library with consumers there

|`REVIEW_APP_ID`
|cuioss-review-bot GitHub App ID
|cuioss-review-bot.yml

|`REVIEW_APP_PRIVATE_KEY`
|cuioss-review-bot private key (.pem)
|cuioss-review-bot.yml

|===

The PR-Agent reviewer needs no Google credential: Gemini is reached through Vertex AI with
Workload Identity Federation, configured by the variables below.

=== Release Apps of Other Organisations

Release propagation reaches a consumer outside cuioss with a release App that belongs to *that*
organisation — private, installed only there. `cuioss-release-bot` is never installed outside
cuioss. Because the propagation runs in cuioss, the foreign App's credentials are stored here:

* `RELEASE_APP_ID_<OWNER>` — the App's numeric ID
* `RELEASE_APP_PRIVATE_KEY_<OWNER>` — a private key of the App

`<OWNER>` is the consumer's owner upper-cased, with every character outside `[A-Z0-9]` replaced
by `_`: `plan-marshall` → `PLAN_MARSHALL`. The names are derived, not configured, so a secret
under any other name is not found.

Give the secrets repository access to every repository that propagates to that owner. A caller
of `reusable-maven-release.yml` additionally has to pass the pair to the workflow. If either
secret is missing or empty, every consumer of that owner is reported as a propagation failure
naming both secrets; there is no fallback to `RELEASE_APP_ID`.

See xref:cuioss-release-bot.adoc#consumers-in-another-organisation[Consumers in another organisation]
for creating such an App.

== Organization-Level Variables

Not credentials, so they are **variables**, not secrets. Set at:
`https://github.com/organizations/cuioss/settings/variables/actions`

[cols="1,2,1"]
|===
|Variable |Purpose |Used By

|`GCP_WIF_PROVIDER`
|Full resource name of the Workload Identity provider the reviewer authenticates through (`projects/{number}/locations/global/workloadIdentityPools/{pool}/providers/{provider}`)
|cuioss-review-bot.yml

|`GCP_REVIEW_SERVICE_ACCOUNT`
|Email of the service account the reviewer impersonates (needs `roles/aiplatform.user`)
|cuioss-review-bot.yml

|`GCP_PROJECT_ID`
|GCP project serving Vertex AI
|cuioss-review-bot.yml

|`GCP_VERTEX_LOCATION`
|Vertex AI location. Optional — defaults to `global`, where the newest Gemini models are served
|cuioss-review-bot.yml
|===

=== Reviewer in Another Organisation

Organization secrets and variables do not cross organisations, and the reusable reviewer workflow
reads both in the *calling* repository's organisation. A repository outside cuioss that calls
`reusable-cuioss-review-bot.yml` therefore needs, in its own organisation:

* the secrets `REVIEW_APP_ID` and `REVIEW_APP_PRIVATE_KEY` (same App, installed there too);
* the variables `GCP_WIF_PROVIDER`, `GCP_REVIEW_SERVICE_ACCOUNT` and `GCP_PROJECT_ID`, plus
`GCP_VERTEX_LOCATION` when the location is not `global`.

Defining the variables is not enough on its own: the Workload Identity provider's attribute
condition and the service account's `roles/iam.workloadIdentityUser` binding must admit that
organisation's repositories, because GitHub's OIDC token names the calling repository. The full
list of prerequisites is in
xref:cuioss-review-bot.adoc#another-organisation[cuioss-review-bot.adoc].

=== Why Keyless?

The reviewer reaches Gemini through **Vertex AI with Workload Identity Federation**: the
workflow's OIDC token is exchanged for short-lived GCP credentials at run time. No Google
credential is stored in GitHub, so there is nothing to rotate or leak. It also draws on the GCP
free-trial credits, which AI Studio does not.

=== Why Organization-Level?

* **Same credentials** - All cuioss repos deploy to same Maven Central account
* **Same signing key** - All artifacts signed with same GPG key
* **Same release bot** - Single GitHub App for all cuioss repos (another organisation's consumers are reached through that organisation's own App)
* **Easier rotation** - Update once, applies everywhere
* **Security** - Fewer copies of sensitive credentials
* **SonarCloud** - Organization uses a single SonarCloud token for all projects
* **Same review bot** - Single GitHub App for every repo that opts into automated PR-Agent review

== npm Publishing (No Token Required)

The `reusable-npm-publish.yml` workflow uses **OIDC Trusted Publishing** instead of a stored npm token.
GitHub's OIDC provider authenticates directly with the npm registry during publish.

* No `NPM_TOKEN` org secret is needed
* Requires `id-token: write` permission in the caller workflow
* Requires an `npm-publish` GitHub Environment configured in the consumer repo
* The npm trusted publisher must be configured on npmjs.com (repository, environment, workflow filename)
* Uses existing `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY` for git tag/push operations only

== Migration Checklist

When migrating repos to the organization:

=== Organization Setup (Once)

* [ ] Add `RELEASE_APP_ID`
* [ ] Add `RELEASE_APP_PRIVATE_KEY`
* [ ] Add `OSS_SONATYPE_USERNAME`
* [ ] Add `OSS_SONATYPE_PASSWORD`
* [ ] Add `GPG_PRIVATE_KEY`
* [ ] Add `GPG_PASSPHRASE`
* [ ] Add `SONAR_TOKEN`

=== Per-Repository Setup

* [ ] Remove any org-level secrets from repo (now inherited)

== Secret Visibility

When adding organization secrets, set repository access to:

* **All repositories** - For secrets used by all repos
* **Selected repositories** - If you need to restrict access

Recommended: Use "All repositories" for the org-level secrets listed above.

== Security Notes

* Never commit secrets to repositories
* Rotate credentials periodically
* Use GitHub's secret scanning to detect leaks
* Organization secrets are inherited but cannot be read by repo admins
* Workflow logs automatically mask secret values
