= Releasing cuioss-organization Workflows
:toc:

== Overview

This document describes how to release new versions of the cuioss-organization reusable workflows.

Releases use **SHA-pinned references** for security - consumers reference workflows by immutable commit SHA, not mutable tags.

== Release Process

=== Triggering a Release

[source,bash]
----
# 1. Update version in .github/project.yml
#    release:
#      current-version: 0.2.0

# 2. Commit and push
git add .github/project.yml
git commit -m "chore: prepare release 0.2.0"
git push

# 3. Trigger the release workflow
gh workflow run release.yml

# 4. Watch the workflow
gh run watch

# 5. Pull the changes made by the workflow
git pull
----

== Files Involved

=== Configuration

[cols="1,2"]
|===
|File |Purpose

|`.github/project.yml`
|Release version and consumer repos list

|`workflow-scripts/update-workflow-references.py`
|Python script to update SHA references in workflow files. Runs twice per release: `--internal-only` before the tag (step 2, owns everything `reusable-*.yml` executes) and unqualified after it (step 4, owns consumer-facing references)

|`workflow-scripts/check-internal-pinning.py`
|Release gate. Fails unless every reference the released workflows execute — composite-action `uses:` pins and the `ref:` of the `workflow-scripts` self-checkout — is a 40-char SHA naming the commit about to be tagged
|===

[NOTE]
====
The order of steps 2 and 3 is load-bearing. Anything a released workflow
executes must be pinned *before* the tag is created; a reference left to step 4
is fixed one commit too late and is correct on `main` but wrong in every tag.
That is what happened to the `workflow-scripts` self-checkout in v0.22.0
through v0.25.0: each tag ran the previous release's scripts, silently, until
v0.25.0 added a script flag the v0.24.0 script rejects.
====

=== Updated by Release

[cols="1,2"]
|===
|File |Updated Content

|`.github/workflows/examples/*.yml`
|Caller templates with SHA-pinned references

|`docs/Workflows.adoc`
|Documentation examples with SHA references

|`README.adoc`
|Root readme workflow examples
|===

== Why SHA Pinning?

[source]
----
                    ┌─────────────────────────────────────┐
                    │         Security Comparison         │
                    └─────────────────────────────────────┘

     Tag Reference (@v1)                    SHA Reference (@abc123...)
    ┌─────────────────────┐                ┌─────────────────────┐
    │                     │                │                     │
    │   v1 ──────┐        │                │   Commit abc123     │
    │            │        │                │        │            │
    │            ▼        │                │        │            │
    │   Commit A          │   Force push   │        ▼            │
    │                     │  ───────────►  │   Immutable         │
    │   v1 ──────┐        │   can change   │   Cannot change     │
    │            │        │   what v1      │   what abc123       │
    │            ▼        │   points to    │   points to         │
    │   Commit B (!)      │                │                     │
    │                     │                │                     │
    └─────────────────────┘                └─────────────────────┘
           MUTABLE                              IMMUTABLE
      (supply chain risk)                      (secure)
----

== Consumer Repo Updates

=== Automatic (via Release Workflow)

Consumer repos listed in `.github/project.yml` automatically receive PRs:

[source,yaml]
----
# .github/project.yml
consumers:
  - cui-java-tools                    # cuioss/cui-java-tools
  - cui-java-parent
  - plan-marshall/plan-marshall-mcp   # a consumer in another organisation
----

An entry is `<repo>` for a cuioss repository, or `<owner>/<repo>` for one in another organisation.

The update runs as the `update-consumers` job, after the `release` job, with one matrix leg per
distinct owner: `update-consumers (cuioss)`, `update-consumers (plan-marshall)`, … An installation
token of the release bot is valid for one account, so each leg mints its own token for its owner
and updates only that owner's consumers. One leg failing does not stop the others, and each leg
writes its own table to the run summary.

=== Manual (via Claude Command)

Use the `/update-github-actions` command to sync workflows to any repo:

[source,bash]
----
/update-github-actions cui-java-tools
----

This copies caller templates from `.github/workflows/examples/` (which already have SHA references) to the target repo.

== Authentication

The release workflow uses `cuioss-release-bot` GitHub App for:

- Pushing tags to protected branches
- Pushing commits that modify workflow files
- Creating PRs in consumer repos

Required permissions on the GitHub App:

- `Contents: Read and write`
- `Pull requests: Read and write` (for opening, labelling and merging the consumer PRs)
- `Workflows: Read and write` (for modifying `.github/workflows/` files)

The token used for pushing, tagging and the GitHub Release is minted for cuioss. Consumer
propagation mints a separate token per consumer owner; see
xref:cuioss-release-bot.adoc#consumers-in-another-organisation[Consumers in another organisation]
for what an organisation other than cuioss must set up.

== Troubleshooting

=== Tag Already Exists

If a previous release attempt failed partway through:

[source,bash]
----
# Delete the tag and retry
git push origin --delete v0.1.0
git tag -d v0.1.0
gh workflow run release.yml
----

=== Release Bot Permission Denied

If you see "refusing to allow a GitHub App to create or update workflow":

1. Go to GitHub App settings for cuioss-release-bot
2. Add `Workflows: Read and write` permission
3. Accept the permission change for installed repos

=== Consumer PRs Not Created

Check that:

1. Consumer repos are listed in `.github/project.yml` — with their `<owner>/` prefix when they are not in cuioss
2. cuioss-release-bot is installed on consumer repos
3. Consumer repos have `.github/workflows/` directory

=== Consumer Reported as "cuioss-release-bot is not installed on '<owner>'"

No token could be minted for that consumer's organisation, so every consumer of that owner is
reported as failed and its `update-consumers (<owner>)` leg is red. Install the App on that
organisation with access to the listed repositories — see
xref:cuioss-release-bot.adoc#consumers-in-another-organisation[Consumers in another organisation] —
then re-run the failed leg.
