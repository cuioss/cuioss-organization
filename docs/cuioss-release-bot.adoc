= cuioss-release-bot
:toc:

== Purpose

GitHub App for automated releases across all cuioss repositories.

Enables release workflows to bypass branch protection rules without granting broad permissions.

Works with any build system (Maven, Gradle, npm, etc.).

== Permissions

[cols="1,1,2"]
|===
|Permission |Access |Reason

|Contents |Read and write |Push commits and tags to protected branches; push the propagation branch to a consumer
|Pull requests |Read and write |Open, label, comment on, close and merge the propagation pull requests in consumers
|Workflows |Read and write |Push commits that change `.github/workflows/` files — every workflow-pin update does
|Metadata |Read-only |Required for all GitHub Apps
|===

These four are the App's whole permission set (`gh api apps/cuioss-release-bot --jq .permissions`).
An installation always receives exactly this set; it cannot be granted per organisation.

== Organization Secrets

[cols="1,2"]
|===
|Secret |Description

|`RELEASE_APP_ID`
|The GitHub App ID (numeric)

|`RELEASE_APP_PRIVATE_KEY`
|The private key (`.pem` file contents)
|===

Set at: `https://github.com/organizations/cui-oss/settings/secrets/actions`

== Repository Setup

For each repository using this bot:

1. **Ruleset**: Add `cuioss-release-bot` to bypass list
+
Settings → Rules → Rulesets → Edit → Add bypass

2. **Workflow**: Use the app token for push operations
+
[source,yaml]
----
- name: Generate Release Token
  id: release-token
  uses: actions/create-github-app-token@v1
  with:
    app-id: ${{ secrets.RELEASE_APP_ID }}
    private-key: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}

- name: Push changes
  uses: ad-m/github-push-action@v1.0.0
  with:
    github_token: ${{ steps.release-token.outputs.token }}
----

== Installation

The app is installed organization-wide on all repositories.

Manage at: `https://github.com/organizations/cui-oss/settings/installations`

== Token Usage

The app token is used for:

* **Maven site deployment** during releases (`reusable-maven-release.yml`)
* **Test report deployment** during integration tests (`reusable-maven-integration-tests.yml`)

Both use `actions/create-github-app-token` with access to the consumer repo and `cuioss.github.io`, replacing the former `PAGES_DEPLOY_TOKEN` PAT.

* **Release propagation** to consumer repositories: the workflow-pin update PRs of a
cuioss-organization release (`release.yml`) and the parent/dependency update PRs of a library
release (`reusable-maven-release.yml`).

An installation token is valid for *one account*. Everything that stays in cuioss — pushes, tags,
Pages — uses a token minted with `owner: cuioss`. Propagation runs one matrix leg per distinct
consumer owner and mints one token per leg, with `owner:` set to that account:

[source,yaml]
----
- name: Generate Propagation Token
  id: prop-token
  if: steps.app.outputs.present == 'true'   # both secrets are set
  continue-on-error: true                   # a failed mint is reported per consumer by the next step
  uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
  with:
    app-id: ${{ secrets[matrix.group.app-id-secret] }}
    private-key: ${{ secrets[matrix.group.private-key-secret] }}
    owner: ${{ matrix.group.owner }}
----

*Which App* mints the token depends on the owner:

[cols="1,2,2"]
|===
|Consumer owner |App |Secrets (in cuioss)

|`cuioss`
|`cuioss-release-bot`
|`RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`

|any other, e.g. `plan-marshall`
|that organisation's *own* release App, e.g. `plan-marshall-release-bot`
|`RELEASE_APP_ID_<OWNER>`, `RELEASE_APP_PRIVATE_KEY_<OWNER>`, e.g. `RELEASE_APP_ID_PLAN_MARSHALL`
|===

`<OWNER>` is the owner upper-cased, with every character outside `[A-Z0-9]` replaced by `_`. The
`read-project-config` action derives both names and carries them in its `consumer-matrix` output;
the workflows index the `secrets` context by them.

`cuioss-release-bot` is private and is never installed outside cuioss. There is no fallback to it:
a foreign owner's secret names always carry the suffix, so missing secrets cannot resolve to the
cuioss App.

== Consumers in another organisation

A consumer listed as `<owner>/<repo>` (see
xref:project-yml-schema.adoc[project-yml-schema.adoc], "Consumer Entry Syntax") receives the same
propagation PRs as a cuioss repository — opened by a release App that belongs to *that*
organisation. Setting one up takes four steps.

. *Create a private GitHub App in the consumer's organisation*, named `<owner>-release-bot`
(`plan-marshall-release-bot`). "Where can this GitHub App be installed?" stays *Only on this
account*. No webhook is needed. Repository permissions — exactly these:
+
[cols="1,1,2"]
|===
|Permission |Access |Reason

|Contents |Read and write |Clone, push the propagation branch, delete it when a stale PR is closed
|Pull requests |Read and write |Open, label, comment on, close and merge the propagation PR
|Workflows |Read and write |Push a commit that changes `.github/workflows/` — every workflow-pin update does
|Metadata |Read-only |Required for all GitHub Apps
|===
+
The name matters: the reviewer workflow skips pull requests authored by
`<owner>-release-bot[bot]` (see <<Where the bot is recognised by its login>>).

. *Install it on that organisation*, with access to every consumer repository listed for that
owner — "All repositories", or "Only select repositories" naming each one. A listed repository
the installation cannot see fails at the clone or the push and is reported as an error for that
consumer.

. *Store its credentials as organisation secrets in cuioss* — not in the consumer's organisation;
the propagation runs in cuioss:
+
[cols="1,2"]
|===
|Secret |Value

|`RELEASE_APP_ID_<OWNER>`
|The App's numeric App ID

|`RELEASE_APP_PRIVATE_KEY_<OWNER>`
|A private key of the App (`.pem` file contents)
|===
+
For `plan-marshall`: `RELEASE_APP_ID_PLAN_MARSHALL` and `RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL`.
The secrets must be visible to every cuioss repository that propagates to that owner —
`cuioss-organization` itself, and each library that lists such a consumer.

. *Let the reusable release workflow see them.* `release.yml` in this repository reads the
`secrets` context directly and needs nothing. A caller of `reusable-maven-release.yml` only sees
what it is given, so a library with a consumer in that organisation passes the pair alongside
its existing secrets:
+
[source,yaml]
----
    secrets:
      RELEASE_APP_ID: ${{ secrets.RELEASE_APP_ID }}
      RELEASE_APP_PRIVATE_KEY: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}
      # … Sonatype and GPG secrets as before …
      RELEASE_APP_ID_PLAN_MARSHALL: ${{ secrets.RELEASE_APP_ID_PLAN_MARSHALL }}
      RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL: ${{ secrets.RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL }}
----
+
GitHub lets a caller pass only secrets the called workflow declares, so each organisation's pair
is declared (optional) in `reusable-maven-release.yml`; a new organisation means adding its pair
there. The alternative is `secrets: inherit`, with which the called workflow sees every secret of
the caller and no declaration is needed — at the price of handing it all of them. A caller with
no consumer in another organisation changes nothing.

Nothing else is needed in the consumer's organisation for the propagation itself: no secrets
there, and no ruleset bypass.

What the propagation PR then meets is that repository's own configuration, the same as in cuioss:

[cols="1,3"]
|===
|In the consumer repository |Effect on the propagation PR

|No ruleset bypass required
|The bot opens a pull request from a branch; it never pushes to `main` there. (The bypass listed
under <<Repository Setup>> is for a repository's *own* release, which pushes to `main`.)

|`skip-bot-review` label
|Applied to the PR so the review bots skip it. If the label does not exist the PR stands and a
warning is logged; the bots may then review it. Create it with `gh label create skip-bot-review`.

|"Allow auto-merge" enabled
|The bot enables auto-merge (or enqueues the PR when `main` has a merge queue). With the setting
off the PR is created but reported as `Auto-merge FAILED (needs manual merge)`. Alternatively
set `github-automation.auto-merge-build-versions: false` in that repository's `project.yml` to
leave the PR open on purpose.

|"Automatically delete head branches" enabled
|The bot never deletes the branch itself (a merge queue rejects that), so without the setting
merged propagation branches stay behind.

|Required reviews
|A ruleset that requires an approving review holds the PR until a human approves it; the bot
cannot approve its own pull request.
|===

=== When it fails

Each owner is its own leg, so one owner failing never stops the others. Every consumer of the
failing owner is listed as an error in the propagation summary, and the leg is red:

[cols="2,3"]
|===
|Message |Cause

|`no release App credentials for '<owner>': consumers of that owner need the secrets
RELEASE_APP_ID_<OWNER> and RELEASE_APP_PRIVATE_KEY_<OWNER>; missing or empty: …`
|One or both secrets do not exist in cuioss, are not visible to the releasing repository, or —
for a caller of `reusable-maven-release.yml` — were not passed. No token is requested.

|`no installation token for '<owner>': the release App from … is not installed on that account
…, or its ID and private key do not match`
|The secrets exist, but the App they belong to is not installed on that owner, or the ID and the
key belong to different Apps. The `Generate Propagation Token` step's log has the API answer.
|===

=== Where the bot is recognised by its login

Propagation PRs in another organisation are authored by `<owner>-release-bot[bot]`, not by
`cuioss-release-bot[bot]`. Everything that singles out the release bot by login has to know that
name too:

[cols="2,3"]
|===
|Place |State

|`reusable-cuioss-review-bot.yml` skip rule
|Skips `cuioss-release-bot[bot]` and `<calling organisation>-release-bot[bot]`. This is why the
App is named by the convention.

|CodeRabbit `auto_review.ignore_usernames`
|Configured per organisation, outside this repository. `cuioss/coderabbit` lists
`cuioss-release-bot[bot]`; an organisation that runs CodeRabbit lists its own bot in its own
configuration. Until then the `skip-bot-review` label is what keeps CodeRabbit off the PR.

|Sourcery
|No author skip exists; the `skip-bot-review` label is the only gate, as in cuioss.

|Dependabot labeller and sweeper
|Not affected: they act on `dependabot[bot]` pull requests and never look for the release bot.
|===

Out of scope here: a repository in another organisation running *its own* release through
`reusable-maven-release.yml`. That workflow's release token is minted with `owner: cuioss`.

== Security Notes

* Private key stored only in GitHub Secrets (never in repos)
* Minimal permissions: Contents, Pull requests and Workflows write — nothing administrative
* A propagation token is minted per consumer owner and never spans two accounts
* `cuioss-release-bot` stays private to cuioss. Another organisation is reached only through its
own private App, so a leaked foreign key exposes that organisation's listed repositories and
nothing in cuioss
* Bypass limited to branch protection, not security rules
