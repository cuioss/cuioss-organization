= Reusable Workflows
:toc:

== Overview

Centralized GitHub Actions workflows for all cuioss repositories.

Eliminates copy-paste duplication and centralizes action version management.

== Workflow Triggers and Duplicate Prevention

=== Maven build — gate-based dedup

`reusable-maven-build.yml` runs on every push and every pull request. A `gate`
job inside the reusable workflow skips a push-triggered build when an open PR
already covers that commit — the PR's own run builds it (producing a Sonar
*pull-request* analysis), so the push build would be redundant. A push to a
branch with **no** open PR still builds (Sonar *branch* analysis + quality), and
the default branch always builds. The caller therefore needs **no `if:`**; it
only grants `pull-requests: read` so the gate can read open PRs:

[source,yaml]
----
on:
  push:
    branches: [main, "feature/*", "fix/*", "chore/*", "release/*", "dependabot/**"]
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pull-requests: read
  actions: read       # covering-run-check job verifies a covering run exists (see #243, #279)

jobs:
  build:
    uses: cuioss/cuioss-organization/.github/workflows/reusable-maven-build.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
----

This gives quality feedback on **every** push, a Sonar pull-request analysis
whenever a PR exists, no push/PR duplicate, and no "stuck PR" when GitHub drops
a push event. The always-green `conclusion` job is the branch-protection
required check, so a gate-skipped push run still reports success.

**The covering `pull_request` run is not guaranteed.** It can be created
several minutes after the push run starts, or never at all — GitHub has been
observed to silently drop the triggering event, and the PR can also close
before its own run starts. A `covering-run-check` job (delegating to
`workflow-scripts/covering-run-check.py`) waits for it and, whenever it
cannot positively confirm one exists, sets a `rescue` signal that makes
*this* push run build the commit itself rather than report an unverified
commit as green — see #279. The rare cost is a duplicate build if the
covering run turns up moments after the rescue decision; the alternative,
before this existed, was a required check that stayed red until a brand-new
commit was pushed.

=== Integration / E2E tests — deferred

The long-running `reusable-maven-integration-tests.yml` suites are deferred:
callers trigger them only on the default branch (post-merge) and on pull
requests — never on every feature-branch push. Because non-default branches are
not in the push list, there is one run per PR update and no push/PR duplicate,
so no caller `if:` is needed:

[source,yaml]
----
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
----

=== npm and pyprojectx builds — same gate

`reusable-npm-build.yml` and `reusable-pyprojectx-verify.yml` carry the **same
`gate` job** as the Maven build: a push to a non-default branch is skipped when an
open same-repo PR already covers the commit, so the caller needs no `if:` and only
adds `pull-requests: read`.

[source,yaml]
----
permissions:
  contents: read
  pull-requests: read

jobs:
  build:
    uses: cuioss/cuioss-organization/.github/workflows/reusable-npm-build.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
----

Like the Maven build, both workflows carry an always-green `conclusion` job that
is the branch-protection required check (`build / conclusion` for npm,
`verify / conclusion` for pyprojectx), so a gate-skipped push run still reports a
green `conclusion` rather than a skipped job.

=== cuioss-organization itself

cuioss-organization is its own consumer: its `python-verify.yml` calls the
reusable pyprojectx verify workflow by **local `./` path** (not a SHA), so it is
intentionally NOT in the `consumers` list and the release bot never opens
SHA-bump PRs for it. It still follows the gate pattern like every other repo —
the caller drops the fork-only `if:`, grants `pull-requests: read`, and requires
`verify / conclusion`. When the gate or `conclusion` contract changes, update
`python-verify.yml` in the same PR as the reusable-workflow change (it picks the
new version up immediately via the local path).

=== Path Filtering for Documentation-Only Changes

The reusable Maven build workflow includes a built-in `check-changes` job using https://github.com/dorny/paths-filter[dorny/paths-filter] that skips build/sonar/deploy jobs when only documentation or config files changed. This is handled entirely inside `reusable-maven-build.yml` — callers do not need any path filtering logic. The same ignore list is also used by `reusable-maven-integration-tests.yml`, via the shared `.github/actions/build-paths-filter-spec` composite action (three independently-maintained copies is exactly how `.gitignore` ended up missing from only one of them). `reusable-pyprojectx-verify.yml` keeps its own static copy of the list instead: this repo's own `python-verify.yml` calls it by *local* path, so it always runs the working-tree version on every PR with no release boundary to hide a stale remote action pin behind.

**Built-in ignored patterns:** `+**/*.adoc+`, `+**/*.md+`, `doc/**`, `.plan/**`, `.claude/**`, `.agents/**`, `.opencode/**`, `opencode.json`, `.vscode/**`, `.gitignore`, `.github/project.yml`, `.github/dependabot.yml`, `LICENSE`, `NOTICE`

Repos with additional non-code directories can extend the ignore list via `project.yml`:

[source,yaml]
----
maven-build:
  skip-on-docs-only: true          # default: true — master switch
  paths-ignore-extra:               # additional patterns to treat as non-code
    - 'e-2-e-playwright/docs/**'
----

The filter also runs on `merge_group`. `dorny/paths-filter` v4 resolves the diff range from the merge-queue event payload (`merge_group.base_sha..merge_group.head_sha`), so the queue evaluates the *entire* merge group against its base branch: a docs-only PR batched alongside a code PR still sees code in the diff and still builds, and only a merge group that is entirely non-code skips. Without this, a docs-only PR skipped the build on `pull_request` and then ran the full build and integration-test suite once queued.

`reusable-pyprojectx-verify.yml` applies its opt-in `skip-on-docs-only` footprint skip to `merge_group` the same way (until v0.32.0 it excluded the queue, so every docs-only PR skipped verify on `pull_request` and then ran a full verify in the queue). It passes `merge_group.base_sha`/`merge_group.head_sha` to paths-filter explicitly and fails open: a filter error, or a missing or non-SHA `base_sha`, runs the full verify. A deliberately skipped queue entry still reports a green `verify / conclusion`, so the queue merges it.

This approach is preferred over workflow-level `paths-ignore` because `paths-ignore` prevents the entire workflow from running, which causes required status checks to never report — blocking PR merges. Each reusable workflow includes a `conclusion` gate job that always runs and reports the aggregate result. Branch protection should require only `build / conclusion` (and `integration-tests / conclusion` for IT repos) instead of individual job names like `build / build (21)`.

NOTE: We intentionally do not use workflow-level `concurrency` with `cancel-in-progress` because GitHub has a https://github.com/orgs/community/discussions/8336[known bug] where cancelled workflows appear as "failed" in PR checks, blocking merges.

=== SonarCloud Quality Gate Enforcement

The `sonar-build` job waits for the SonarCloud Quality Gate result and fails if the gate fails.
This ensures PRs with insufficient coverage or other quality issues cannot pass CI with a green check.

* Quality Gate failure blocks the PR (sonar-build reports as failed)
* Snapshot deployment is skipped when sonar-build fails
* Dependabot PRs are unaffected (Sonar analysis is skipped for Dependabot by default)
* SonarCloud's default timeout of 300 seconds applies
* To disable Sonar analysis entirely, set `sonar.enabled: false` in `project.yml`

=== Quarkus / smallrye-config Alignment

The `quarkus-alignment` job asserts that every `io.smallrye.config` artifact the project
resolves matches the smallrye-config release that the project's effective `version.quarkus`
manages. It runs in parallel with `build` and is enforced through the `conclusion` gate.

**Why it is needed.** `java-ee-10-bom` pins `io.smallrye.config:*`, and those pins can beat the
`io.quarkus:quarkus-bom` a consumer imports. Quarkus' deployment classes are compiled against one
specific smallrye-config release, so a mismatch fails augmentation at runtime with
`failed to access io.smallrye.config.ConfigMappingLoader$ConfigMappingImplementation`. Nothing is
split from Maven's point of view, so `requireSameVersions` is correctly silent and the build stays
green — the failure only appears when an application starts. It has shipped through
`cuioss-parent-pom` twice.

**Why a parent-side gate cannot replace it.** Both inputs are consumer-side facts:

* Consumers compose their own BOMs. Import order decides which smallrye pin wins, and that order
  lives in the consumer's POMs. TokenSheriff, for example, imports `quarkus-bom` ahead of its own
  `token-sheriff-bom` (which reaches `java-ee-10-bom`); reversing those two lines changes which
  version resolves, with no change to any parent.
* `cui-quarkus-parent` explicitly *supports* a consumer overriding `version.quarkus` for an
  emergency pin. That moves `quarkus-bom` but not `java-ee-10-bom`'s inherited smallrye pin — so a
  supported, documented action produces the split while the parent-side check still passes.

**How it decides.**

* `version.quarkus` is read from the *effective* POM (`help:evaluate`), never by scanning `pom.xml`
  text. Consumers inherit it from `cui-quarkus-parent` and declare it nowhere, so a text scan
  reports "not declared anywhere" and the gate becomes the one people wave through.
* The expected version is the `io.smallrye.config:smallrye-config` entry published in
  `io.quarkus:quarkus-bom:<version.quarkus>` on Maven Central.
* The assertion is made against the *resolved classpath* (`dependency:list`), not a declared
  property. That catches a **split** family (two smallrye versions in one reactor) as well as a
  uniformly wrong one.
* `io.quarkus:quarkus-core` is checked against `version.quarkus` too: the property drives
  `quarkus-maven-plugin` (a build extension) while the artifacts come from whichever BOM is
  imported, and those two inputs can drift apart independently of smallrye.

**Behaviour.**

[cols="1,3"]
|===
|Outcome |Meaning

|Pass
|Every resolved `io.smallrye.config` artifact matches, or no such artifact is on the classpath.

|Skip
|`version.quarkus` is undefined in the effective POM — not a Quarkus project. Costs one
`help:evaluate` and nothing more; no `dependency:list` runs.

|Fail
|A resolved artifact does not match, or `quarkus-core` has drifted from `version.quarkus`.

|Fail
|The check could not determine alignment (Maven Central unreachable, an unreadable POM, a timeout).
"Cannot determine" is blocking by design — an unresolvable check is not a pass.
|===

There is no opt-out: a non-Quarkus project skips itself, and a Quarkus project that cannot be
checked is exactly the case the gate exists for.

=== Snapshot Publish Verification

`mvn deploy` exiting `0` proves Maven finished without error — not that a newer snapshot reached
the repository. TokenSheriff run https://github.com/cuioss/TokenSheriff/actions/runs/34214468714[34214468714]
published nothing for four days while `deploy-snapshot` reported green or cancelled, because a
parallel reactor deadlocked inside the `central-publishing-maven-plugin`'s cross-module
coordination (`-T1` on the deploy step now prevents that specific deadlock). Nothing checked the
*result* of a deploy that runs to completion without one — that is what this step closes
(cuioss/cuioss-organization#278).

**How it decides.** Immediately before `mvn deploy` runs, the job reads the project's own root
`groupId:artifactId` — a safe "representative artifact" present in every reactor build regardless
of packaging — from its version-level `maven-metadata.xml` on the Central Publishing snapshot
repository (`https://central.sonatype.com/repository/maven-snapshots/`). After the deploy step, it
reads the same metadata again and fails the job unless the published
`<versioning><snapshot><timestamp>` both:

* advanced past the pre-deploy reading (skipped when nothing was published there yet — the first
  deploy of a new module or a freshly bumped `-SNAPSHOT` version has nothing to compare against),
  and
* is not older than the moment this deploy started (a stale read of leftover metadata from a prior
  run is not evidence of *this* run's publish).

This only runs when `project.version` ends in `-SNAPSHOT`; the deploy step itself is a no-op
otherwise (see the `conclusion` note below).

**Making a silent skip visible.** The `conclusion` job could previously only tell that
`deploy-snapshot` did not fail — a job-level skip (snapshot deploy disabled for the repo) and a
job that ran but published nothing (a non-`-SNAPSHOT` version on the default branch, e.g.
immediately after a release, before the next dev-version bump) both looked identically green. On
the default branch, `conclusion` now emits an `::notice::` naming which of the two happened, so a
deliberate no-op reads as deliberate instead of silently green.

=== GITHUB_TOKEN for Maven Steps

A build that resolves artifacts — its parent POM included — from a GitHub Packages Maven registry
needs a token on *every* Maven invocation: that registry never answers anonymously. Such a
repository commits a `.mvn/settings.xml`, activated by `-gs .mvn/settings.xml` in
`.mvn/maven.config`, that takes the credentials from the environment:

[source,xml]
----
<settings>
  <servers>
    <server>
      <id>my-org</id>
      <username>${env.GITHUB_ACTOR}</username>
      <password>${env.GITHUB_TOKEN}</password>
    </server>
  </servers>
</settings>
----

`GITHUB_ACTOR` is a default variable of every step; `GITHUB_TOKEN` is not. Opt in with:

[source,yaml]
----
maven-build:
  github-token-env: true
----

Every step that runs Maven then starts it with `GITHUB_TOKEN` set to the workflow token: the
matrix build, the Quarkus alignment check, the snapshot deploy and its `help:evaluate` steps here,
the test step of `reusable-maven-integration-tests.yml`, and the release step of
`reusable-maven-release.yml`. The `sonar-build` step is unaffected — it has always set
`GITHUB_TOKEN`, with or without the key.

**Off is exactly as before.** The default is `false`, and with it Maven starts with the
environment it had before the key existed — `GITHUB_TOKEN` is *absent*, not empty. The steps do
not use `GITHUB_TOKEN: ${{ <on> && github.token || '' }}`, which would define an empty variable
when off: Maven interpolates `${env.GITHUB_TOKEN}` to an empty password where it would otherwise
leave the expression unresolved, and build plugins and tests that probe the variable would see it
defined. The token travels in a carrier variable that a two-line preamble exports as
`GITHUB_TOKEN` when it is non-empty and then unsets. It is not written to `GITHUB_ENV` either,
which would hand it to every later step of the job rather than to the Maven process alone.

**Permissions.** The workflows' own permissions do not change, and neither does what a caller
grants:

* Resolving packages of a *public* repository of the same organisation works with the workflow
  token as it is — no `packages` permission is needed.
* Resolving packages of a *private* repository does **not** work with another repository's
  `GITHUB_TOKEN`, whatever permissions the caller grants: the token is scoped to the repository
  the workflow runs in, and the build fails with HTTP 401/403 on the first artifact it resolves.
  These workflows pass no other credential to Maven, so such a dependency is not supported.

=== Publishing to GitHub Packages

By default snapshots go to Maven Central. A repository whose POM names a GitHub Packages registry
in its `distributionManagement` (`https://maven.pkg.github.com/<org>/<repo>`) sets:

[source,yaml]
----
maven-build:
  github-token-env: true            # resolving from the registry, see above
  deploy-target: github-packages
  packages-server-id: my-org        # the repository id in distributionManagement; default: github
  maven-profiles-snapshot: ''       # what the snapshot deploy needs; may be empty
  maven-profiles-release: ''
----

With `deploy-target: github-packages` the `deploy-snapshot` job of this workflow is skipped, and
with it every Maven Central step: the `central` server, the `central.sonatype.com` origin patch,
the Sonatype and GPG secrets, and the snapshot publish verification. This workflow then publishes
nothing. The publish runs in `reusable-maven-github-packages-deploy.yml`, called from a second job
of the consumer's workflow:

[source,yaml]
----
jobs:
  build:
    permissions:
      contents: read
      pull-requests: read
      actions: read
    uses: cuioss/cuioss-organization/.github/workflows/reusable-maven-build.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
    secrets:
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  deploy-snapshot:
    needs: build
    if: needs.build.outputs.github-packages-deploy == 'true'
    permissions:
      contents: read
      packages: write
    uses: cuioss/cuioss-organization/.github/workflows/reusable-maven-github-packages-deploy.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
----

**Why a second job.** A GitHub Packages deploy needs `packages: write` on the job's token. A
called workflow can only *restrict* the caller's token, and GitHub checks that statically: a job
that requests a permission its caller does not grant fails the whole run at startup, before any
job executes and regardless of the job's `if:`. A `packages: write` job inside
`reusable-maven-build.yml` would therefore break every Maven Central consumer — none of them grants
it — the way `actions: read` did in v0.21.0. So the permission is requested only in a workflow that
only GitHub Packages consumers call, and the Maven Central caller contract is unchanged.

The `github-packages-deploy` output keeps the decision in one place: it is the condition of
`deploy-snapshot` with the deploy target inverted, so a snapshot is published to GitHub Packages
under exactly the conditions it would be published to Maven Central.

The empty profile lists are deliberate. The defaults (`release-snapshot,javadoc` and
`release,javadoc`) activate signing and the `central-publishing-maven-plugin` in the cuioss parent
POM; a GitHub Packages consumer sets what it needs instead. An empty list produces no `-P` argument
at all.

See <<Maven Deploy to GitHub Packages>> for the workflow, and
link:workflow-examples/maven-github-packages-caller.yml[maven-github-packages-caller.yml] for the
complete caller.

== Maven Release

    secrets:
      RELEASE_APP_ID: ${{ secrets.RELEASE_APP_ID }}
      RELEASE_APP_PRIVATE_KEY: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}
      OSS_SONATYPE_USERNAME: ${{ secrets.OSS_SONATYPE_USERNAME }}
      OSS_SONATYPE_PASSWORD: ${{ secrets.OSS_SONATYPE_PASSWORD }}
      GPG_PRIVATE_KEY: ${{ secrets.GPG_PRIVATE_KEY }}
      GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}
----

=== Release Guard

The trigger above fires on **any** merged edit to `.github/project.yml`. That file also
carries `maven-build`, `sonar`, `pages`, `github-automation`, `consumers` and
`dependency-propagation`, so an ordinary Java-version bump matches the `paths:` filter too,
and `if: github.event.pull_request.merged == true` does not tell the two apart. On
2026-07-12 exactly that shape published an irrevocable `de.cuioss.sheriff.api:*:1.0.0`.

`reusable-maven-release.yml` therefore runs a `guard` job before anything else. The trigger
has to stay in each caller — GitHub evaluates an `on:` block only in the calling repository —
but the decision is central, so every caller gets it on a pin bump and none has to wire
anything up.

`reusable-npm-publish.yml` is guarded identically: the same `guard` job running the same
`release-guard` action, the same `fetch-depth: 0` / `fetch-tags: true` checkout, and its
`publish` job gated on `needs.guard.outputs.proceed == 'true'`. An npm publish is as
irrevocable as a Maven Central deploy, so the table below applies to both paths. The npm
path tags `v<version>`, a form the already-tagged check counts.

[cols="1,2"]
|===
|Invocation |Outcome

|`workflow_dispatch`
|Proceeds unconditionally, including a re-release of an unchanged version. The deliberate
path is never blocked.

|Merged PR, `release.current-version` unchanged
|**Skipped.** A no-op, not a failure — the caller's run stays green.

|Merged PR, version changed, tag already exists
|**Skipped.** `release:prepare` never writes `current-version` back to `project.yml`, so a
revert or a re-merge of a version-bump PR genuinely changes the value and would otherwise
release an already-published version a second time.

|Merged PR, version changed, untagged
|Proceeds.

|PR closed without merging
|**Skipped**, regardless of the version.
|===

Anything the guard cannot decide — an unreadable `project.yml`, an unresolvable first parent,
a version string that is not a usable version — fails the job. Blocking a release is visible
and recoverable; publishing to Maven Central or npm is not.

==== What a caller sees when the guard skips

The `release` job and everything downstream of it are skipped, so the workflow's outputs are
empty strings.

The calling job's `result` is **not** a usable signal for this. The guard job itself ran and
succeeded, so the called workflow's run has one successful job and several skipped ones —
which GitHub reports as `success`. A caller-side job written as

[source,yaml]
----
if: needs.release.result == 'success'   # WRONG — true even when nothing was released
----

runs anyway, with every output empty. Test the output instead:

[source,yaml]
----
if: needs.release.outputs.released-version != ''
----

Here `needs.release` is the *caller's own* job — the one whose `uses:` points at this
workflow — not the `release` job inside it; caller jobs cannot reach a called workflow's
internal jobs at all.

NOTE: The guard checks out with `fetch-depth: 0` and `fetch-tags: true`. Both are
load-bearing: at `actions/checkout`'s default depth of 1 there is no first parent to compare
against and no tags to check, and the guard would read "unchanged" forever — green for the
same reason a deleted test is green.

=== Releasing to GitHub Packages

With `maven-build.deploy-target: github-packages` (see <<Publishing to GitHub Packages>>) the
`release` job prepares, tags and pushes the release, and publishes nothing:

* The JDK is set up without a server and without a GPG key; the `central` server and its
  `central.sonatype.com` origin patch are skipped.
* The Maven step runs `release:prepare` and, when the site is deployed, the site build — but not
  `release:perform`, which is the publish. No Sonatype or GPG secret reaches it. `GITHUB_TOKEN` is
  always set on it.
* `wait-for-maven-central` is skipped. `propagate-to-consumers` still runs — it does not depend on
  that job's success — and its summary says that availability was not checked.

The artifacts are published from the tag by `reusable-maven-github-packages-deploy.yml`, called
from a second job, for the reason given under <<Publishing to GitHub Packages>>:

[source,yaml]
----
jobs:
  release:
    permissions:
      contents: write
    if: github.event.pull_request.merged == true || github.event_name == 'workflow_dispatch'
    uses: cuioss/cuioss-organization/.github/workflows/reusable-maven-release.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
    secrets:
      RELEASE_APP_ID: ${{ secrets.RELEASE_APP_ID }}
      RELEASE_APP_PRIVATE_KEY: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}

  publish:
    needs: release
    if: needs.release.outputs.released-version != ''
    permissions:
      contents: read
      packages: write
    uses: cuioss/cuioss-organization/.github/workflows/reusable-maven-github-packages-deploy.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0
    with:
      ref: ${{ needs.release.outputs.released-version }}
----

Three consequences of the split:

* **The tag exists before the artifacts do.** In a Maven Central release `release:perform` publishes
  first and the push follows. Here a failed `publish` job leaves a tagged, unpublished release; it
  is repaired by re-running that job, not by releasing again — the release guard refuses a version
  that is already tagged.
* **A release version is deployed once.** The registry refuses a second deploy of the same version
  with HTTP 409. A `publish` job that failed part-way through a multi-module reactor cannot simply
  be re-run: the modules already published are refused. Delete those package versions first.
* **Propagation can outrun the publish.** `propagate-to-consumers` starts when the `release` job
  ends, while the caller's `publish` job is starting. A consumer PR opened in that window fails to
  resolve the new version until the publish has finished, and then needs a re-run.

The publish is `./mvnw deploy -DskipTests` on the tag, with the profiles of
`maven-build.maven-profiles-release`. It is not `release:perform`: `releaseProfiles`, `goals` and
`arguments` configured for the `maven-release-plugin` do not apply to it.

NOTE: This workflow mints its release token with `owner: cuioss`. A repository in another
organisation cannot run its own release through it, whatever the deploy target — see
xref:cuioss-release-bot.adoc[cuioss-release-bot.adoc].

See link:workflow-examples/maven-release-github-packages-caller.yml[maven-release-github-packages-caller.yml]
for the complete caller.

=== Automatic Dependency Propagation

The Maven release workflow can automatically propagate version updates to consumer repositories after release. This is configured in the library repo's `project.yml`:

**Example: Parent POM propagation** (e.g., `cui-java-parent` releases a new version):

[source,yaml]
----
# scope: parent — no property hints needed
consumers:
  - cui-java-tools
  - cui-core-ui-model

dependency-propagation:
  group-id: de.cuioss
  artifact-id: cui-java-parent
  scope: parent
----

**Example: Dependency/property propagation** (e.g., `cui-test-juli-logger` releases a new version):

[source,yaml]
----
# scope: dependency — each consumer must include :property-name
consumers:
  - cuioss-parent-pom:version.cui.test.juli.logger

dependency-propagation:
  group-id: de.cuioss.test
  artifact-id: cui-test-juli-logger
  scope: dependency
----

**How it works:**

1. After the Maven release completes, the workflow waits for the artifact to appear on Maven Central (up to 30 minutes)
2. The `propagate-to-consumers` job runs one matrix leg per distinct consumer owner and mints one release-bot token per leg, because an installation token is valid for one account
3. For each consumer repo of that owner, it clones the repo, updates the POM version, creates a PR, and enables auto-merge
4. Stale PRs from previous version updates are automatically closed with a "Superseded" comment

**Consumers in another organisation:**

A consumer entry may be qualified with its owner, with or without a hint:

[source,yaml]
----
consumers:
  - cui-java-tools                                      # cuioss/cui-java-tools
  - plan-marshall/plan-marshall-mcp:cui-quarkus-parent  # another organisation
----

A bare name stays a cuioss repository. A consumer in another organisation is reached with that
organisation's *own* release App, never with `cuioss-release-bot`. Its credentials are cuioss
organisation secrets named `RELEASE_APP_ID_<OWNER>` and `RELEASE_APP_PRIVATE_KEY_<OWNER>`
(`<OWNER>` upper-cased, every character outside `[A-Z0-9]` as `_`), and the releasing repository
passes them to this workflow next to the secrets it already passes:

[source,yaml]
----
    secrets:
      # … the six required secrets …
      RELEASE_APP_ID_PLAN_MARSHALL: ${{ secrets.RELEASE_APP_ID_PLAN_MARSHALL }}
      RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL: ${{ secrets.RELEASE_APP_PRIVATE_KEY_PLAN_MARSHALL }}
----

Both are optional and declared per organisation in this workflow. A repository with no consumer
in that organisation passes neither. See
xref:cuioss-release-bot.adoc#consumers-in-another-organisation[Consumers in another organisation].
Without the two secrets — or when the App behind them is not installed on that owner — that
owner's leg reports each of its consumers as failed, naming the secrets, and is red; the other
legs are unaffected.

**Scopes:**

* `parent` — Updates the `<parent><version>` in the consumer's root `pom.xml`. No property hints needed.
* `dependency` — Updates a named version property across all POM files. Each consumer entry **must** include a `:property-name` suffix (e.g., `cuioss-parent-pom:version.cui.test.juli.logger`).

`wait-for-maven-central` uses `continue-on-error: true`. `propagate-to-consumers` deliberately does not: the artifact is already published when it runs, so it cannot block the release, but a consumer that did not get its PR is a failure that has to be visible.

With `maven-build.deploy-target: github-packages`, `wait-for-maven-central` is skipped and the artifact is *not* yet published when `propagate-to-consumers` runs — see <<Releasing to GitHub Packages>>.

== Maven Deploy to GitHub Packages

Publishes a Maven project to the GitHub Packages registry named in its POM's
`distributionManagement`, with the workflow token: no Sonatype credentials, and no GPG key unless
`maven-build.sign-artifacts` is `true`. It is the publishing half of
`maven-build.deploy-target: github-packages` and refuses to run for any other deploy target.

=== How It Authenticates

`actions/setup-java` writes a server with the id `maven-build.packages-server-id`, the username
`${env.GITHUB_ACTOR}` and the password `${env.GITHUB_TOKEN}` — variable names, never values. Every
Maven step of the job sets `GITHUB_TOKEN` to the workflow token. The id must equal the repository
id in the POM's `distributionManagement`.

=== What Is Verified

The exit code of `./mvnw deploy`, and nothing is read back afterwards. The registry answers a
deploy synchronously, so a rejected upload fails Maven: a release version that already exists is
refused with HTTP 409, a missing permission with 403. A repeated deploy of a `-SNAPSHOT` version
succeeds. This is unlike Maven Central, where a green deploy could publish nothing and the
<<Snapshot Publish Verification>> exists for that reason.

=== Verifying the merge-queue footprint skip

The gate's decide and `conclusion` logic is exercised by `test/workflow/test_pyprojectx_gate.py`, which runs the real step bodies under bash. The end-to-end behaviour needs a consumer with `skip-on-docs-only: true` and a merge queue (e.g. `cuioss/plan-marshall`):

. Queue a PR that changes only `.md`/`.adoc`/`.plan/**` files. In the `merge_group` run, `gate` logs `Only non-building (docs/config) files changed — skipping verify`, `verify` is skipped, and `verify / conclusion` is green, so the entry merges.
. Queue a PR that changes a `.py` file. In the `merge_group` run, `gate` outputs `run=true`, and the full `verify` job runs.

== Dependabot Auto-merge

=== Basic Usage

[source,yaml]
----
name: Dependabot Auto-merge

on:
  pull_request:

jobs:
  auto-merge:
    uses: cuioss/cuioss-organization/.github/workflows/reusable-dependabot-auto-merge.yml@bf0f1305123c16521d9fdcf2a9474e3cdb981caa # v0.37.0 # <version>
    permissions:
      contents: write
      pull-requests: write
----

By default, this marks **all** Dependabot PRs for **minor and patch** updates as eligible. Major updates require manual review. For a grouped update, eligibility is decided by the *highest* semver step in the group, so a group containing one major update is excluded.

=== How the Merge Happens

Auto-merge runs in two parts, in two different identities:

. **This workflow labels.** It runs in the consumer repo on the Dependabot PR, evaluates the update-type policy, and applies the `automerge` label. It never merges.
. **The org sweeper merges.** `dependabot-sweeper.yml` in `cuioss-organization` runs every 15 minutes, mints a `cuioss-release-bot` App token, and merges every labelled PR that GitHub reports as ready. On a merge-queue repo that enqueues; elsewhere it merges directly.

The split is not stylistic. A Dependabot-triggered workflow only ever holds `GITHUB_TOKEN`, and GitHub starts no workflow runs for events created by `GITHUB_TOKEN`. Under a required merge queue that makes the token structurally unable to land a PR: either the queue entry never receives its `merge_group` check runs and is dropped when `check_response_timeout_minutes` expires, or the auto-merge request is recorded and never converts into a queue entry. Both leave a green, mergeable PR open indefinitely. An App token is not `GITHUB_TOKEN` and is not subject to that rule.

A Dependabot-triggered workflow also cannot read Actions secrets, so it cannot mint the App token itself — which is why the sweeper is scheduled centrally rather than added to each consumer repo.

=== Inputs (Optional)

[cols="1,1,1,2"]
|===
|Input |Type |Default |Description

|`allowed-dependency-pattern`
|string
|`` (all dependencies)
|Substring to match in dependency names. Empty string matches all dependencies.

|`allowed-update-types`
|string
|`minor,patch`
|Comma-separated semver update types to auto-merge (`major`, `minor`, `patch`)
|===

The label name is deliberately *not* an input. The sweeper searches for the
literal `automerge`, so a per-repo override would produce labelled PRs it never
finds — labelled, unmerged, and reported as nothing to do.

=== Turning It Off Per Repository

Set the switch in the repo's `.github/project.yml`:

[source,yaml]
----
github-automation:
  dependabot-automerge: false
----

The sweeper skips the repo and reports it as opted out.

Omitting the key means participation. A repo without the caller workflow is
never labelled *automatically*, so it normally produces no candidates — but a
label can also be applied by hand (see below), so absence of the caller is a
default, not a guarantee. This switch is the only explicit opt-out.

A `project.yml` that exists but cannot be read or parsed is treated as
*indeterminate*, not as participation — the sweeper declines to merge and says
so. A definite absence is an answer; an unreadable config is not.

=== Who Can Be Merged

Two independent gates, both required:

* The labelling job runs only when `github.actor == 'dependabot[bot]'`.
* The sweeper searches with `--author app/dependabot` and merges only PRs whose
  head branch starts with `dependabot/`.

The author cannot be forged: `dependabot[bot]` is an App-derived login, GitHub
usernames admit no brackets, and App slugs are globally unique. The branch check
is defence in depth — a label survives a force-push, so a collaborator could
otherwise reuse an already-labelled Dependabot branch for unrelated content.

Note that the update-type policy is enforced only on the labelling path. Anyone
with write access can hand-apply `automerge` to a Dependabot PR the policy would
have rejected, and the sweeper will merge it once its required checks are green.
That is a deliberate manual override, not an oversight.

=== No Secrets Required

The caller uses the default `GITHUB_TOKEN` — it only labels. The App credentials live with the sweeper in `cuioss-organization`.

=== Merge Queue Repositories

Every workflow that produces a *required status check* must also subscribe to the `merge_group` event:

[source,yaml]
----
on:
  pull_request:
    branches: [main]
  merge_group:
----

Without it the queue entry never receives those check runs, waits out `check_response_timeout_minutes`, and is dropped — taking any auto-merge request with it.

The caller templates for the workflows that produce required checks — Maven build, Maven integration tests, npm build, pyprojectx verify — carry the trigger. Templates for workflows that never produce a required check (dependency review, scorecards, PR-Agent, releases, the Dependabot labeller) deliberately do not. A repo that promotes a new check to *required* has to add the trigger to that workflow itself.

Repos on the org-managed merge queue must not also require *branches to be up to date before merging*. The queue is what brings an entry up to date; requiring it beforehand makes a PR's readiness depend on a condition the queue itself satisfies, and readiness is what the sweeper waits on. `setup-branch-protection.py` enforces this: any repo listed in `merge_queue.merge_queue_repos` gets `strict_required_status_checks_policy: false`.

=== Recommended: Dependabot Cooldown

For supply chain security, add a cooldown to your `.github/dependabot.yml` to delay updates and allow time for community detection of compromised releases.

The block is *ecosystem-specific* — it is not the same for every entry.

For `maven`, `pip` and `npm`, which support per-semver-level tiering:

[source,yaml]
----
    cooldown:
      default-days: 3
      semver-major-days: 7
      semver-minor-days: 3
      semver-patch-days: 1
----

For `github-actions` and `docker`, `default-days` only:

[source,yaml]
----
    cooldown:
      default-days: 3
----

Do *not* add the `semver-*-days` keys to `github-actions` or `docker` for symmetry. Dependabot rejects them for those ecosystems, and a single rejected property invalidates the *entire file* — which disables Dependabot version updates repo-wide, not merely for the offending entry.

If an entry *already* has a `cooldown` block, do not assume it is correct — an existing block is the likely defect rather than evidence of a healthy config, because earlier guidance told operators to add the tiered block to every entry. Audit each `github-actions` and `docker` entry and delete any `semver-*-days` keys it carries, keeping `default-days`.

Dependabot reports this as a *check-run* named `.github/dependabot.yml`, not an Actions run, so a green build does not cover it. After any change to the file, read the check-run on the resulting commit on `main`:

[source,bash]
----
gh api repos/cuioss/<repo>/commits/<sha>/check-runs \
  --jq '.check_runs[] | select(.name==".github/dependabot.yml")
        | {status, conclusion, summary: .output.summary}'
----

To audit a repo you have *not* just changed, read the check-run on the commit that last touched the file — the check only re-runs when `dependabot.yml` changes, so a broken config goes on reporting nothing on every later commit:

[source,bash]
----
SHA=$(gh api "repos/cuioss/<repo>/commits?path=.github/dependabot.yml&per_page=1" --jq '.[0].sha')
gh api "repos/cuioss/<repo>/commits/$SHA/check-runs" \
  --jq '.check_runs[] | select(.name==".github/dependabot.yml")
        | {status, conclusion, summary: .output.summary}'
----

Only `status: completed` with `conclusion: success` is a pass. Empty output means the check has not run on that commit — not that the file is valid.

== cuioss-review-bot Review

Third automated PR reviewer for the org, beside CodeRabbit and Sourcery, running the
open-source PR-Agent on Google Gemini under the cuioss-review-bot identity with a
security-weighted charter. Gemini is reached
through *Vertex AI* with *Workload Identity Federation* — keyless, and it draws on the GCP
free-trial credits.

Adoption is *opt-in per repository*: a repo is reviewed only once it carries the caller
workflow below.

The workflow is not tied to the cuioss organisation. The App token's owner, the settings
repository and the organization variables all resolve in the *calling* repository's organisation,
so a repository elsewhere can call it once that organisation has its own prerequisites in place —
see xref:cuioss-review-bot.adoc#another-organisation[Using the reviewer from another organisation].

=== Skip Rules

Enforced as the reusable workflow's job-level `if:` guard, *not* by PR-Agent configuration —
its `ignore_pr_labels` / `ignore_pr_authors` settings are read only by its webhook servers and
are ignored entirely in GitHub Action mode. A guarded-out pull request consumes no runner
minutes and no tokens.

* `dependabot[bot]` pull requests — gated by CI and auto-merge already.
* `cuioss-release-bot[bot]` pull requests — consumer-propagation and workflow-SHA bumps.
* `<owner>-release-bot[bot]` pull requests, `<owner>` being the calling repository's organisation —
the same bumps in an organisation other than cuioss, where they are authored by that
organisation's own release App (`plan-marshall-release-bot[bot]`).
* Any pull request labelled `skip-bot-review` — the shared org-wide manual opt-out.
* Fork pull requests — secrets are unavailable to them; reviewing forks would require
`pull_request_target` and a separate security review of that decision.

An explicit `/review` comment from a human overrides the skip label — someone is asking on
purpose. There is no automatic re-review on push; request one with a `/review` comment.

A second skip runs upstream of the review, in the workflow's `changes` job, on the `pull_request`
path only. It skips the review when the pull request leaves the reviewer nothing to read:

* A pull request with no files.
* A pull request whose whole diff the reviewer's own diff-file filter removes — the `[ignore]`
globs and regex of the org and repository `.pr_agent.toml`, then PR-Agent's invalid-extension
filter, which also drops auto-generated lockfiles. A `.plan/**`-only diff is one such case, and
so is `.gitignore` plus `.plan/**`, which the `[ignore]` globs alone would leave standing.

The decision is computed by PR-Agent's own code, not by a copy of its filter lists:
`workflow-scripts/classify-review-diff.py` runs PR-Agent's settings loader and its diff-file
listing inside the same pinned reviewer image, and logs one
`classify-review-diff: reviewable=… survivors=… settings=…` line naming the decision, the number of
files left after filtering, and the settings sources it read. Every failure to decide fails
*open* into the review — the job then logs a `classify-review-diff fail-open:` notice with the
reason, or, if it crashed, leaves no decision at all, which the review job reads as reviewable.

The `changes` job carries the same four org skip terms as the review job, so it does not run —
and pulls no reviewer image — on a pull request no review can run on. The regression suite pins
the two lists in lockstep.

=== Verification

PR-Agent cannot report its own failure: its action runner catches exceptions and exits `0`, so a
run whose every model call failed reports success. A fail-closed step therefore verifies the
reviewer's own structured output (the `review` output of whichever reviewer step ran,
`review_central` or `review_assembled`), which is written before the
publish decision — never a published comment. Whether a clean review publishes anything is a
`cuioss-review-bot` settings tuning decision, not a property of this workflow, and the comment is
persistent and updated in place, so a stale one would satisfy a naive check forever. The
structured output is the only oracle that holds however that repository is configured.

The check covers automatic `pull_request` runs whose action is one the runner actually reviews —
`opened`, `reopened`, `ready_for_review` and `review_requested`, the runner's own allow-list —
plus `/review` comments. Those four are exactly the caller template's `pull_request` `types:`
above, and that alignment is a contract rather than a coincidence: PR-Agent's
`github_action_config.pr_actions` is configurable from a repo-local `.pr_agent.toml` or from the
org file in `cuioss/cuioss-review-bot`, so narrowing it makes the check assert on actions the
runner no longer reviews, and widening it makes the check silently stop covering the added
action. Changing `pr_actions` therefore means changing the guard's allow-list and the caller
template in the same edit. The regression suite pins the part this repository can observe — the
allow-list is exactly that set, the template subscribes to all of it, and nothing here overrides
`pr_actions`; that the settings repository does not override it either is a convention, not an
enforced invariant. It is scoped by command rather than by event, because `/ask` and `/help`
write no review output at all. The `/review` path is the one consumers depend on for a
re-review — including automation that posts the command programmatically — so leaving it
unverified would have reproduced the same false green on the path that matters most.

Every other `pull_request` action is deliberately outside the check. The runner returns before
any tool runs on them, so an empty output is the correct outcome rather than a failure — and the
check could not cover them in any case, because the runner emits no output, exit code or marker
distinguishing a legitimate skip from a total model failure, which leaves its precondition
unevaluable there rather than merely unmet. Two narrower populations — a pull request with no
files, and an empty diff after filtering — arise on reviewed actions, and are skipped upstream by
the `changes` job (see the Skip Rules above), so the review, and with it the check, does not run for
them. That is possible only because their discriminator is computable from the pull request's
file list before the review starts; after the reviewer ran, nothing distinguishes them from a
failure. When the `changes` job cannot decide, it fails open, and such a pull request reaches the
check and fails it, as it always did. The workflow's own `EXCLUDED` comment block carries the full
enumeration.

=== Concurrency

Nothing is ever cancelled (`cancel-in-progress: false`), per the org-wide policy noted above.
The concurrency group is keyed on the *trigger*, not the pull request:

* Comment-triggered runs group per comment id. Each slash-command is a distinct explicit
request, so two of them must never collapse into one group.
* `pull_request` runs group per pull request number, since every reviewed action is a redundant
notification about the same state.

This shape is load-bearing, not incidental. Concurrency is evaluated at workflow level, *before*
the job's `if:` guard, so a group keyed on the pull request alone lets any comment — including
ones the guard then skips, and including the reviewer's own published review — cancel a review
that is mid-flight. That leaves the worst possible outcome: the reviewer publishes, but the
fail-closed step that verifies it actually produced a review is skipped.

The accepted trade-off is that two reviews requested seconds apart may run concurrently and both
update the persistent review comment, last write winning.

See xref:automatic-review/pr-agent.md[automatic-review/pr-agent.md] for the review anatomy and
signal-vs-noise breakdown, and
xref:cuioss-review-bot.adoc[cuioss-review-bot.adoc] for the App.
